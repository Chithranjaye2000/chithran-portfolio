## Connection and save behavior

- Contact uses a separate lazy mysql2 Promise pool with verified CA/hostname checks and TLS 1.2+. It never falls back to local MySQL if Aiven configuration or connectivity fails.
- Development reads the existing ignored `backend/.env.aiven` as explicit Contact database configuration. The file's `DB_*` values are not merged with local database settings.
- Production requires the separate `CONTACT_DB_*` process environment settings below. It does not read workstation environment/certificate files as a fallback. Optional catalogue APIs retain the original `DB_*` pool, while frontend Projects/QA use static data.
- Existing validation, 32 KB JSON limit, five-request/IP/15-minute limiter, parameterized INSERT, and sanitized errors remain. The database insert completes before email sending is attempted and awaited.
- A confirmed save returns `201` with `saved: true`. SMTP acceptance produces `notification: "sent"`; missing/failed SMTP produces `notification: "unavailable"`, preserves the saved message, and logs a fixed warning without credentials or message contents. SMTP acceptance is not proof of inbox delivery.
- The frontend's synchronous submission lock and disabled fieldset prevent duplicate requests while pending. This is not durable exactly-once delivery across reloads, multiple tabs, or retries after an unconfirmed timeout. There is no background mail retry/outbox in this change.

## Contact-only schema

The reviewed `backend/database/contact-schema.sql` contains only `contact_messages`: the existing eight-column design, primary key, two secondary indexes, and three enforced CHECK constraints. It has InnoDB and explicit `utf8mb4_unicode_ci` defaults. New timestamps are generated by the Aiven server, inspected as UTC; no historical local-time values were imported.

The setup script reads the isolated Aiven file, requires verified TLS, checks whether the table exists, and validates columns/types/defaults, exact indexes, CHECK definitions/enforcement, engine/collation, and unexpected triggers/foreign keys. It creates the table only if absent. Incompatible existing objects cause a safe failure; no automatic ALTER, DROP, TRUNCATE, repair, or record import occurs.


This was run successfully after checking the target: only the Contact table was created, initially with zero records. A rerun after verification preserved it and its new record. Do **not** run the general `db:init`, `db:migrate:projects`, or `db:migrate:qa` commands against Aiven for this feature. The earlier full-database migration plan remains unapproved and outside this scope.

## Gmail configuration on your computer

1. Enable Google 2-Step Verification on the Gmail sender account, then open [Google App Passwords](https://myaccount.google.com/apppasswords) and create one for portfolio notifications. Use an App Password, never your regular Gmail password. App Passwords may be unavailable on some managed or Advanced Protection accounts; see [Google's requirements](https://support.google.com/mail/answer/185833?hl=en).
2. Enter the following privately in the Git-ignored `backend/.env.smtp`. This separate file avoids changing your working `.env` or `.env.aiven`:

```dotenv
SMTP_HOST=smtp.gmail.com
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=your_sender@gmail.com
SMTP_PASSWORD=your_google_app_password
SMTP_FROM=your_sender@gmail.com
CONTACT_NOTIFICATION_EMAIL=your_recipient@gmail.com
```

3. Set `CONTACT_NOTIFICATION_EMAIL` to **your actual recipient address**. It is never inferred from the public profile. For Gmail, `SMTP_FROM` can be blank to use `SMTP_USER`; if supplied, it must match. Google displays the 16-character App Password in groups; ordinary grouping spaces are removed. Alternatively use port `587` with `SMTP_SECURE=false`, which requires STARTTLS. Certificate verification remains enabled for both modes.
4. Start the existing applications in separate PowerShell terminals:

```powershell
Set-Location -LiteralPath 'D:\SLT QA\My_Portfolio\backend'
npm run dev
```

```powershell
Set-Location -LiteralPath 'D:\SLT QA\My_Portfolio'
npm run dev
```

5. Open `http://127.0.0.1:5173/`, submit a clearly labelled new test, and confirm the saved acknowledgement. Check the recipient's Inbox and Spam folders separately before claiming delivery. Do not expose App Passwords, SMTP debug output, or certificate contents when reporting failures.

Outside production, `.env.smtp`, if present, is the complete SMTP configuration; it is not partially merged with other secrets. Explicit configuration objects in tests remain independent of that file. If the file is absent, existing development SMTP environment settings are supported. Production ignores `.env.smtp` and requires `CONTACT_NOTIFICATION_EMAIL`; legacy `SMTP_TO` is only a development fallback.

Gmail accepted a notification during the earlier local Contact implementation verification, but Gmail can block unfamiliar server locations or impose sending limits. That historical check does not establish delivery from the current Preview. For sustained production reliability, consider OAuth2 or a dedicated SMTP provider using the same transport configuration; do not weaken TLS or use a regular Gmail password. See [Nodemailer's Gmail guidance](https://nodemailer.com/guides/using-gmail).

## Production environment values

Configure secrets in the existing Vercel project's server environment settings, not frontend-prefixed variables or committed files. Contact uses these names; the static frontend requires no catalogue `DB_*` configuration:

| Setting                      | Required value                                                                       |
| ---------------------------- | ------------------------------------------------------------------------------------ |
| `NODE_ENV`                   | `production`                                                                         |
| `FRONTEND_ORIGIN`            | Exact allowed frontend HTTPS origin, without a path or wildcard                      |
| `CONTACT_DB_HOST`            | Exact Aiven service DNS hostname                                                     |
| `CONTACT_DB_PORT`            | Aiven service port                                                                   |
| `CONTACT_DB_NAME`            | Database containing the prepared Contact table                                       |
| `CONTACT_DB_USER`            | Prefer a restricted Contact runtime account                                          |
| `CONTACT_DB_PASSWORD`        | Its database password                                                                |
| `CONTACT_DB_SSL_ENABLED`     | `true`                                                                               |
| `CONTACT_DB_SSL_CA`          | Full downloaded PEM CA/bundle; preferred for Functions                               |
| `CONTACT_DB_SSL_CA_PATH`     | Alternative securely provisioned runtime file path; leave empty when using inline CA |
| `SMTP_HOST`                  | `smtp.gmail.com` or the chosen SMTP provider                                         |
| `SMTP_PORT`                  | `465` for the prepared Gmail configuration                                           |
| `SMTP_SECURE`                | `true` for port 465; `false` with required STARTTLS on 587                           |
| `SMTP_USER`                  | Gmail sender address                                                                 |
| `SMTP_PASSWORD`              | Google App Password, not regular password                                            |
| `SMTP_FROM`                  | Optional for Gmail; defaults to and must match `SMTP_USER`                           |
| `CONTACT_NOTIFICATION_EMAIL` | Your recipient inbox address                                                         |

Use exactly one Contact CA source. A Windows CA-file path will not exist on a hosted function; configure the PEM value or provision a secure runtime file. Do not set any database/SMTP value with a `VITE_` prefix. Use a separate setup account for CREATE; the runtime Contact operation needs INSERT on this table, not general schema-management privileges. Confirm provider account/grant choices before launch; this task does not change users or grants.

## Vercel deployment steps — require approval

1. Keep the existing project and use the checked-in Services configuration: root Vite `app` plus Express `backend` rooted at `backend`. Do not create another project. The `src/app.js` default Express export is the serverless handler; `server.js` remains local-only. See the [Services guide](vercel-services-deployment.md) and [Express on Vercel](https://vercel.com/docs/frameworks/backend/express).
2. Configure the backend production values above and an appropriate Node runtime. Keep certificates and environment files private; do not upload local secrets through Git. Allow sufficient function duration for database plus awaited SMTP timeouts, choose a region appropriate for Aiven, and budget pooled connections across concurrent instances. The current Contact pool retains five connections per warm instance; scaling multiplies that number. If the separate catalogue pool is also configured, include its connections in the total budget. See [Vercel pooling guidance](https://vercel.com/kb/guide/connection-pooling-with-functions).
3. Before public launch, configure an **enforcing cross-instance rate-limit/WAF rule for POST `/api/contact`**, or a suitable shared limiter. The application limiter remains bounded per process and resets on cold starts; it is not a global serverless quota. The Contact limiter trusts a single validated `x-vercel-forwarded-for` IP only under the platform's `VERCEL=1` runtime flag. Other runtimes ignore that header, and global Express `trust proxy` remains disabled. Do not manually set `VERCEL=1` outside the trusted platform. See [Vercel request headers](https://vercel.com/docs/headers/request-headers) and [WAF rate limiting](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting).
4. For same-origin Services, leave **both `VITE_API_BASE_URL` and `VITE_CONTACT_API_BASE_URL` unset/empty** so Contact posts to `/api/contact` on that deployment. Neither value should contain `/api`; the request already includes it. Projects/QA render static data and make no catalogue requests. Keep local `.env` unchanged; do not copy workstation URLs into Vercel or migrate catalogue records to Aiven.
5. Confirm CORS, an actual save, SMTP acceptance, and receipt in the intended inbox from the deployed origin. Vercel supports SMTP on 465/587; the send remains awaited before responding. See [Vercel SMTP guidance](https://vercel.com/kb/guide/serverless-functions-and-smtp). Do not call the production deployment ready until secrets, rate limiting, connection budgets, routing, and this end-to-end check are configured.
